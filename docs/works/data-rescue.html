The card is not dead until you write to it

Getting photographs off an SD card, USB stick or hard drive that has started to fail — without destroying them in the attempt. The order of the steps is the whole method, and the first thing to do is nothing.

Stop writing to it. Now.

Before any tool, any friend's advice, any "repair" a camera or a laptop offers you: take the card out and stop using it. Every photograph you take, every file the machine saves, every folder the system rebuilds is written over space that may still hold something you want. The project that makes the recovery tool says this in capital letters:

As soon as a picture or file is accidentally deleted, or you discover any missing, do NOT save any more pictures or files to that memory device or hard disk drive; otherwise you may overwrite your lost data.CGSecurity, PhotoRec project page

If the device is what your computer boots from, stop using the computer and work from another one. If it holds the only copy of something irreplaceable, read the rest of this page first and then decide whether to touch it yourself at all.

First, work out which failure you have

Three different problems get called "the card is dead", and only two of them are recoverable by a person with a laptop. Answer this honestly before you start, because the wrong answer costs data.

What you seeWhat it usually isWhat to do
Everything is there, but the card/stick "needs to be formatted", or shows as RAW / unreadable, or the letters turn into gibberish Damage to the file system — the index — while the files themselves are probably still on the media The method below. Do not accept the format prompt.
Some photos open, some are corrupt, copying is very slow, or the computer freezes mid-copy Failing hardware or worn-out flash cells. The device is dying while you read it The method below, but the imaging step matters more than the recovery step, and every full read of the device shortens its life.
The device is not detected at all, or it makes clicking, beeping or grinding noises Controller or mechanical failure Stop. Nothing on this page can help. A drive that makes noise is a cleanroom job; unplug it and keep it unplugged. unverified here — this is the one recommendation on this page not taken from a fetched source

The method

The idea is one sentence: make a byte-for-byte copy of the device once, then do all your experiments on the copy. A failing device gets exactly one careful read, not one per recovery tool you try. Everything below is that idea, in order.

Step 1

Do not let anything "repair" it

No chkdsk, no Disk Utility "First Aid", no fsck, no "fix" button in a camera. Repair tools assume the index is wrong and rebuild it — on a drive that is failing, that means writing to the drive you are trying to read. The manual for the imaging tool says it in one line:

Never try to repair a file system on a drive with I/O errors; you will probably lose even more data.GNU ddrescue manual, "Important advice"

It also warns about the milder version of the same mistake — a mounted device is a device the operating system is writing to:

Never try to rescue a r/w mounted partition. … It is best that the device or partition to be rescued is not mounted at all, not even read-only.GNU ddrescue manual, "Important advice"

Step 2

Get a second disk with at least as much free space as the whole device

Not the same free space as the files you want — the size of the entire card or drive, because step 3 copies the whole thing including the empty parts. A 128 GB card needs 128 GB free. On macOS or Linux this is usually an external disk; on Windows, an external or a second internal drive. The destination gets overwritten, and the manual is blunt about what happens if you aim it wrong:

If you use a device or a partition as destination, any data stored there will be overwritten.GNU ddrescue manual, "Important advice"

Name the destination as a file (card.img), never as a device (/dev/sdb, /dev/diskN). A file cannot wipe a disk by accident; a device name can, and the mistake is one letter wide.

Step 3

Image the device, once, with ddrescue

ddrescue is free, runs on Linux, macOS and Windows (via Cygwin or WSL), and is built for exactly this: reading a device that only partly works. Install it from your package manager (brew install ddrescue, apt install gddrescue, dnf install ddrescue). Then find the device's name — on macOS diskutil list, on Linux lsblk — and be sure of it before you type the next line.

# macOS: rdiskN is the raw device, which skips a buffering layer
sudo ddrescue -d -r3 /dev/rdiskN card.img card.map

# Linux: /dev/sdX or /dev/mmcblk0 — the whole device, not a partition number
sudo ddrescue -d -r3 /dev/sdX card.img card.map

What each part is doing, from the manual's own option list:

  • -d (--idirect) uses direct disc access, "bypassing the kernel cache" — the read comes from the media instead of from memory the system kept. The manual warns that "Not all systems support this" and that sector size must be set correctly; if your machine does not support it, ddrescue says so, and you drop the -d.
  • -r3 (--retry-passes=3) makes three extra passes over the parts that failed. This flag is not optional in practice — see "one thing the tool will not do for you" below.
  • card.map is the mapfile, and it is what makes the tool resumable — "Also you may interrupt the rescue at any time and resume it later at the same point." The manual's own words are that "The mapfile is an essential part of ddrescue's effectiveness. Use it unless you know what you are doing."

It is normal for this to take hours on a failing card, and normal for it to be slow and then fast. Let it finish. If it is interrupted, run the same command again — it picks up where it stopped, because of the mapfile.

Step 4

Read the result as a report, not as a success or a failure

ddrescue ends with a summary of how much it rescued and how much it could not. Anything it could not read is a real loss; everything else is now safe on your second disk, and the original device can be set aside and left alone. From here on you work on card.img only. The card itself can go in a drawer.

Step 5

Recover files from the copy with PhotoRec

If the file system is damaged — step 1's first row — no amount of copying will make the photos list themselves, because the index that names them is the broken part. PhotoRec is the tool that ignores the index completely and looks for the files themselves:

PhotoRec ignores the file system; this way it works even if the file system is severely damaged.CGSecurity, "How PhotoRec works"

Point it at the image file and give it an output folder on a different disk, which comes from the same project's warning:

… while using PhotoRec, you must not choose to write the recovered files to the same partition they were stored on.CGSecurity, PhotoRec project page
photorec card.img
# choose the image, then the file types (default: all), then an output folder
# on a DIFFERENT disk from card.img

On macOS and Windows this is the TestDisk/PhotoRec package from the project's step-by-step page, which walks through the arrow-key menus.

Step 6

Expect files without names, and sort them by date

Anything recovered by carving comes back renamed — f0001234.jpg — and usually in a folder per file type. What survives is the content and, for photographs, the EXIF date taken, which is how you sort them back into order. Batch tools that rename by EXIF date exist on every platform. What is lost is the folder structure and the original filenames, permanently.

What this method does not do

  • It cannot bring back overwritten data. If you kept shooting after the photos vanished, those files are gone — that is what the red box at the top is for.
  • It does not restore filenames or folders for anything recovered by step 5. The files are yours again; the organisation is not.
  • It does not fix hardware. A device that is not detected, or that clicks or grinds, needs a laboratory, and every attempt at home reduces what a laboratory can get.
  • It does not work on encrypted volumes. BitLocker, FileVault, LUKS and phone-internal storage hand you unreadable bytes; the key is the problem, not the media.
  • It is not a backup. A method for surviving a failure is not the same as not having one. Two copies on two devices, one of them somewhere else, is the actual answer to the problem this page is about.

One thing the tool will not do for you

A detail that surprises people, and it is in the manual's option list rather than hidden: -r n --retry-passes=n — "Exit after the given number of retry passes. Defaults to 0." Left at its default, ddrescue reads every block once and gives up on the ones that failed. The same page explains why that is not the same as giving up: "To retry bad sectors detected on a previous run, you must specify a nonzero number of retry passes." That is why the command in step 3 carries -r3. A second run with a higher number is safe at any point, because the mapfile remembers which blocks are still outstanding.

Where two honest sources pull in different directions

Not a contradiction, but a real tension a reader will meet, so both sides are named rather than resolved by choosing one.

ddrescue's manual wants the failing device not mounted at all, not even read-only; the PhotoRec documentation, and most guides that explain it, start from a device the computer has already mounted and shown you. The two describe different moments. The strict rule is also the safe one: unmount first, then image. A read-only mount is far less dangerous than a read-write one, but the manual's position is that "the resulting copy may be useless" even then, and nothing in the recovery step needs the card mounted — the imaging tool reads the device, and PhotoRec reads the image file.

Two things on this page are reasoning rather than quotation, and are marked so a reader can weigh them separately from the quoted text: that the three-way triage table is the useful first question, and that the noise rule in its third row is a stop rule. Both are mine, not the sources'.
