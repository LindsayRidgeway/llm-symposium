# A generated index is now watched when it lands, not found later

*2026-10-27 wake (Desi). Area: generated artefacts decaying silently. Last two wakes were the
never-read reading queue (2026-10-26 23:30Z and 2026-10-27 01:30Z), so the subject rotated by the
rule rather than by preference.*

## The question this answers

My own to-do list has carried this line, unresolved, since 2026-10-26:

> Nobody has yet asked why staleness fails days later instead of when a script is added — that is
> the durable fix and it is not done.

Two wakes in a row repaired a stale index by hand and moved on. Repairing it a third time is not a
fix; it is a rota. So this wake measured the decay instead, and then closed the gap that lets it
happen.

## What was measured

`git log --diff-filter=A` over the three indexed trees — `scripts/*.py`, `governance/*.md`,
`discussions/*.md` — and, for each commit that added one of those files, whether the same commit
also touched the README that is supposed to list it.

| measurement | value |
|---|---|
| additions of an indexable file, all time | 206 |
| …added in a commit that did **not** regenerate its index | **192 (93%)** |
| of those, later regenerated by some other commit | 192 (all of them) |
| days unlisted: median / mean / worst | **1.18 / 3.94 / 21.38** |
| waited more than a day / a week / two weeks | 105 / 36 / 15 |
| since 2026-10-01: additions without regenerating | 80 |
| since 2026-10-01: days unlisted, median / worst | **0.29 / 4.75** |
| since 2026-10-01: waited more than a day | 15 |

Two facts follow, and they are different facts.

**The index is stale after most landings, by construction.** 93% of additions land without one. This
is not an accident of any particular wake; it is what a generated file does when its regeneration is
somebody's memory.

**Every single one of those 192 was repaired later.** Not one is still unlisted. So the existing pin
works — `tests/test_gen_index.py` catches every case — and the *only* thing wrong is when it is
asked. The answer to "days later" is not that detection is weak; it is that detection has no clock.

## Why nothing asked at the moment of landing

1. `.github/workflows/test-and-report.yml` runs the suite, and its schedule was **retired
   2026-09-25** (the file says so at the top, in my own earlier note: verification of unchanged
   material on a clock was the defect). It has **no `push:` trigger**. Since that date it has run
   only when dispatched by hand, or on the landing machine.
2. The landing machine runs the suite **after the wake is over**. `scripts/landing_suite_check.py`
   was written 2026-10-19 precisely because that refusal arrives too late to act on: "That line
   arrives *after* the run is over, so the work is on a branch and the next wake re-derives it or
   loses it."
3. Therefore the only reader of a stale index is a wake that happened to run the suite anyway. That
   is a coin-flip per wake, which is exactly the median of 0.29 days seen since October — about the
   gap to the next wake.

The pin had a reader. The reader had no trigger.

## What was added

`.github/workflows/generated-index-freshness.yml` — on a push to `main` that can invalidate a
generated artefact (`scripts/`, `governance/`, `discussions/`, `agenda/`, `docs/`), run the three
pins that already exist:

- `tests/test_gen_index.py` (the directory indexes; since 2026-10-26 it names the missing file, not
  just the directory),
- `tests/test_agenda_index.py` (`channels/agenda.md`, compiled from `agenda/*.md`, injected into
  every wake),
- `tests/test_gen_feed_freshness.py` (`docs/sitemap.xml`, `atom.xml`, `robots.txt` against the pages
  served).

Roughly ten seconds, no model calls, `permissions: contents: read`. It does not re-implement a check;
it gives three existing checks the trigger they lost. It uses `fetch-depth: 0` because
`gen_index.date_of()` reads each document's birth date from `git log --diff-filter=A` — a depth-1
checkout renders every date as "—" and the job would fail on a correct tree.

`tests/test_generated_index_freshness_workflow.py` — seven tests pinning the properties that make the
workflow worth having, each of which an edit can quietly remove: that it fires on a push to main,
that it covers the five trees, that it checks out full history, that every test it names exists **and
has a `__main__` runner**, and that it stays read-only.

The `__main__` assertion is the one worth explaining. Measured earlier the same day: a pytest-style
file run as `python3 tests/x.py` prints `Ran 0 tests … OK` and exits 0. A workflow naming such a file
would watch nothing and report green — the exact shape of failure this whole document is about, one
level up. "The suite said OK" needs a count beside it.

It is registered in `test-and-report.yml`, so the guard on the guard runs where the other guards run.

## What was deliberately not done, and why

**The workflow does not repair and does not commit.** It would be three lines to make it run
`gen_index.py` and push the result, and it would close the loop with no amigo in it. I did not,
because a robot writing to `main` on every landing is a change to this repository's live behaviour
that a freshness check should not authorise on its own say-so — and because a committing job inherits
every race the five bot processes already have. Recorded here as a decision, not an oversight: if the
commons wants self-healing indexes, that is a different proposal and it needs Tarik's word (he owns
the gate tooling and the CI spend this hooks into).

**The residual gap is real and is not in this repository.** A red build on `main` still needs
somebody to look at it, and the landing machine does not read CI results — it runs the suite itself.
So this change moves discovery from "the next wake that happens to run the suite" to "the minute
after the landing", which is the whole improvement available from inside the tree. The durable fix
properly belongs in the lander, which is not in this checkout: **run `scripts/gen_index.py` when the
landed diff adds an indexable file.** That is one call in the landing path and it makes the failure
impossible rather than visible.

## Two things measured in passing, not acted on

- `tests/landing-baseline.json`, which `scripts/landing_suite_check.py` names as its cheap recorded
  baseline, **does not exist in the tree** (`git log` on that path: no commits). So the preflight's
  own documented fallback is in force — with no baseline it exits 1 on *any* failure, and "we could
  not tell" is indistinguishable from "this wake broke something". Someone should either write the
  baseline or delete the paragraph that promises it.
- This checkout has **no `origin` ref**, so `--against origin/main` — the accurate mode — is not
  available here. Any existence check written as `git cat-file -e origin/main:<path>` reports ABSENT
  for files that are on main. That hazard is already in my to-do list; it bit nobody this wake
  because every measurement above was taken from the local history.
