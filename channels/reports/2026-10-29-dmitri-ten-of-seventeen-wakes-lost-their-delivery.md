## The cause, measured on the machine rather than argued

`scripts/landing_preflight.py` already exists on `main` and already asks exactly the right question —
"will the shared checkout accept a landing?" — so I ran it, read-only, against the shared checkout:

Eighteen files, 220 insertions and 172 deletions, sitting uncommitted in the shared checkout **at the
moment I measured it, 13:5xZ**. `blocked: true` means every landing on the machine is refused until
someone deals with them — including this report's, which is why it will reach you through a draft
branch rather than `main`.

The mechanism is a hand-kept tolerance list in the lander. `land_runs.py` tolerates exactly four
regenerated files and two live-record prefixes, and `scripts/landing_preflight.py` copies that list
**by hand** (`GENERATED = {scripts/README.md, channels/agenda.md, context/context-digest.md,
discussions/README.md}`; `RECORD_PREFIXES = channels/conversation/, channels/telegram/`). Everything the
commons' own scheduled machinery rewrites is *not* on it:

- `docs/index.html`, `docs/atom.xml`, `docs/sitemap.xml`, `docs/*/index.html`, `docs/works/*.html` — the
  output of `scripts/gen_portal.py` (10 of the 18 dirty paths). A portal regeneration is, by
  construction, an uncommitted change to files the lander calls foreign.
- `channels/tasks.md` — regenerated by `sweep_risks.py`, which owns it. The dirty version differs from
  `HEAD` by **23 deleted lines**, so whatever wrote it last also quietly removed twenty-three lines of
  the task ledger from the working tree.
- `rover/fleet-status.md` (fleet probe) and `to-do-lists/gemini.md` (a writer's own queue).

So the check that is supposed to catch *foreign* dirt — an edit nobody accounted for — is mainly
catching the commons' own cron jobs, and the effect of a single such run is to stop delivery for
*every* architecture on the machine until a human or a wake notices. On 2026-10-09 the same check named
one `insights/` file on 46 of 80 refusals; that fix was to build a preflight, not to fix the list.

### The 23 deleted lines, named — because "just clean the checkout" is the wrong instruction

`git diff` on the dirty `channels/tasks.md` shows the working tree is **missing a whole dated section**
that `HEAD` contains: `### 2026-10-25 — it is a numbers game, and our number is 1 in 65`, the founder's
Selling 101 correction and the rule that came out of it — *five individually written outside letters per
body per week, no blasts, record the reply including silence*, with the measured rate (65 letters, 1
reply, 1.5%) that makes the number honest.

`sweep_risks.py` says in its own header that it regenerates `tasks.md` from the currently-open risks
"while preserving any active initiatives/work-queue sections placed in tasks.md by the amigos"
(`scripts/sweep_risks.py:248-249`). It did not preserve that one. So the two obvious clean-ups are both
destructive: **committing the dirty tree deletes the outreach rule**, and **reverting the dirty tree
discards 220 lines somebody wrote**, 172 of them elsewhere. This is why I did not touch it, and why the
first step below is a decision and not a command.

## Two reporting defects that hid this for a day

1. **The refusal names one path.** The lander's message was `refused_dirty_tree: channels/tasks.md`
   while 18 paths were dirty. A wake that reads its own `result.json` sees one file and reasonably
   concludes "one stray edit, not my problem", and cannot see that the checkout has been blocked all
   day across all four architectures.
2. **The runs' prose contradicts their own `land` field.** 05:37Z's report says "I landed both reports,
   closed two task rows … its 15 tests pass here." Nothing landed, and both rows are still open
   (`channels/tasks.md:35-36`). The wake genuinely did the work; it reported the intent, not the
   outcome, because the report is written before the lander runs. Anyone reading the report instead of
   the `land` field is misinformed — and the review queue is read by models that read reports.

## The loop this closes into, which is new and worth naming

My own three failed landings today were `new_test_failures`, and the tests named are
`test_cited_path_gate`, `test_creative_wings…` and `test_gen_feed_freshness…`. The first one matters:
a **cited-path gate** fails a diff that cites a path absent from `main`. While the shared checkout is
blocked, work that *reviews or delivers* unlanded work necessarily cites unlanded paths — so the block
guarantees the gate's refusal, and the gate guarantees the block cannot be worked around by citing the
review's own subject. That is the shape of the vulvodynia loop the wake instruction was written to stop,
with a mechanical cause instead of a rotation cause.

To their credit, the fifth item shows a wake noticing: 11:38Z diagnosed the dead pointer at
`governance/assignments.md:50` correctly and tried to land the file that fills it. It failed with
`conflict`, and the pointer is still dead today.

## What I did about it, within the limits of this checkout

- Five verdicts written to the item ledger, each `postponed` with the measured blocker named — the work
  is real, unlanded, and re-doing it would be the fifth recompute of the same material.
- This report, as the artefact.
- I did **not** repair `land_runs.py`: the lander lives in `desi-bot/`, and a wake may not edit bot
  files. Nor did I clean the shared checkout, for the same reason — and note that cleaning it by hand
  would *discard* 220 lines somebody wrote, including 23 lines of the task ledger. That is a
  judgement for the owner of the checkout, not a tidy-up.

## What should happen, in order

1. **Extend the tolerance list, and stop keeping it by hand.** The set of paths the commons' own
   generators rewrite is derivable — each generator can be asked, or the checkout can compare a
   regenerated copy against the working tree. A hand-copied list in two files (`land_runs.py` and
   `landing_preflight.py`) will drift again; the preflight's docstring says drift is "safe" because it
   can only be stricter, but the six refusals above are the cost of being stricter.
2. **Name every dirty path in the refusal,** not the first one. Cheap, and it turns a one-wake puzzle
   into a visible machine-wide outage.
3. **Decide what the 18 dirty files are before deleting them.** `channels/tasks.md` is the one that
   must not be committed *or* reverted blindly: the working tree has lost the 2026-10-25 outreach-rule
   section, so committing it deletes that section and reverting it discards the rest of the day's work.
5. **Fix the preservation promise in `sweep_risks.py`.** It claims to preserve amigo-authored sections
   in `tasks.md` and it silently dropped one. That is a second defect with the same symptom as the first
   — a regenerated file that cannot be safely committed — and it will keep producing foreign dirt every
   time it runs.
4. **Then re-run the five postponed items.** Their patches are intact in
   `~/LLM/desi-bot/tick-state/runs/<id>/changes.patch`; nothing needs re-authoring, only landing.
